# #446 decision report — deterministic browser replay

## Current result and recommendation

The owner-approved, pinned offline replay ran the official `@json-render/react` 0.21.0 renderer in Chromium 148.0.7778.96. It used hand-authored specs, one stable React root and state store, three frozen scenarios, four sequential stages, four styling arms, and two deterministic repeats: **96 measured rows**. The runner made no model calls. The [replay report](evidence/replay.json) and [48 first-repeat screenshots](evidence/shots/) are the measured evidence; the older [blocked preflight](offline-preflight.json) and [post-install preflight](evidence/preflight-after-install.json) are historical dependency checkpoints, not measured failures.

| Arm | Valid spec, DOM, edited input, focus, action, theme, unchanged host | Expected layout style | Samples with missing expected style |
| --- | --- | --- | --- |
| Fixed catalog variants | 24/24 for every listed measure | 24/24 | 0 |
| Bounded catalog props | 24/24 for every listed measure | 24/24 | 0 |
| Utility `className` + BaroCSS preload | 24/24 for every listed measure | 24/24 | 0 |
| Utility `className` + initial build CSS only | 24/24 for every listed measure | 6/24 | 72 |

Each row has an immediate computed-style sample in the same browser task as mount/edit, then three animation-frame samples. The build control's 72 misses are four samples each for 18 repeated later-stage cells; they show **persistent absent CSS**, not a transient flash. Its initial stage passed in all six repeated cells. The utility and build arms share the same 28-token initial stylesheet inventory, official renderer, component tree and semantic edits. The fixed and bounded arms precompile their full 31-token variant inventory. The representative [utility](evidence/shots/settings--utility--responsive.png) and [build control](evidence/shots/settings--build--responsive.png) settings screenshots show the same content with different later-stage spacing.

**Decision:** This replay supports the existing BaroCSS class preload helper when a catalog admits utility tokens that are absent from the initial build CSS. It does **not** show an advantage over a fixed or bounded catalog whose variants are fully known and compiled. State, focus and action preservation belong to the official renderer/store/host integration, not to BaroCSS. No new package, adapter, UI layer or public API follows from these 48 distinct cells. A narrow example using the existing helper is the smallest possible next product candidate, subject to Planner priority. The live-model reliability study below still needs separate owner approval of provider, model, cost and safety boundary.

The replay was run twice from the exact issue command. Both complete runs produced byte-identical [`replay.json`](evidence/replay.json) (SHA-256 `1657d752fe7d44c0c5cc7a894e72a846e898a2e7249924ce071890fa8b90fbd6`) and screenshot aggregate manifest (SHA-256 `324ffee92d9087efdb945216f5e62ef2093cd6a7cfed8bed5234c8b429af7fd4`). [`verify.mjs`](verify.mjs) passed 96 rows, 48 screenshots and the frozen control inventory; four contract tests passed. Exact package versions, transitive integrities, source/bundle separation and browser executable hash are in [`INSTALL-PLAN.md`](INSTALL-PLAN.md) and [`evidence/environment.json`](evidence/environment.json). Independent Review of the final commit is still pending.

**Limits:** Specs and edits were authored by the experiment, not generated by a model. Style checks cover layout padding, gap, columns and two theme colors; the host check samples five computed properties. The responsive stage uses a narrow desktop Chromium viewport, not a mobile device. One browser build and two replay repeats do not establish cross-browser, accessibility or live-model reliability. Synchronous preload before each mount/edit is part of the measured integration; arbitrary streaming or delayed insertion may differ. The prior #376 study had one output per format/model/request and cannot fill these gaps.

## At the offline checkpoint: unmeasured outcomes and attribution

No scenario has a rendered screenshot, computed-style comparison, input/focus/action result, frame count or host-style delta from this phase. No cell is a pass. The absence of an official renderer prevents attribution of any hypothetical failure to catalog expressibility, React state handling, CSS generation, or BaroCSS. The prior one-shot study used worker-authored references, heuristic visual checks and one output per cell; prompt wording, catalog choice and reference tuning are alternative explanations for its scores.

Once dependencies are available, the runner must first verify schema/DOM/state. A missing component or changed user value/focus before an action is a renderer/state failure. If DOM and state are correct but computed style or stylesheet insertion is wrong, the failure is styling. A click-induced blur is expected browser behavior, so focus is recorded before the action click. Both failures together, missing timing evidence, or a blocked dependency are mixed/unknown. An unstyled-frame claim requires frame-by-frame evidence, not only a final screenshot. Host impact requires before/after computed style of an unchanged host sentinel.

Install pinned official json-render core/React and their React peer dependencies in an isolated research directory, plus a pinned Playwright core and browser executable. Record exact package versions, resolved tarball integrity, browser version, OS, Node version, BaroCSS commit and theme CSS hash. No other renderer is an acceptable substitute. Independent Review must reproduce representative cells and inspect any failure attribution.

### Step 2: live-model reliability study, after a separate owner cost/safety approval

Freeze the three scenario briefs, catalog prompts, theme, edit instructions, JSON spec schema, examples, fixture hash above, random seeds (0–4), model IDs and generation settings before calling a model. Use 5 independent sessions per scenario × 3 styling arms × 2 tiers = **90 sessions**. Each session has initial generation plus three edits, for **360 responses**. Use the same user-input state at each edit; do not give the model hidden outcomes from another arm. Pair arms by scenario, seed and model tier. The build-only control replays the utility arm's exact outputs with its initial-stage class inventory, so it adds no model calls.

Candidate tiers for cost planning are Claude Haiku 4.5 and Sonnet 5. These are provisional model IDs, not authorization or an assumption about CLI billing. Set an operational cap of 3,000 billed input tokens and 1,000 billed output tokens per response; abort a session that cannot fit without truncating required context. At 180 responses per tier, the cap is 540,000 input and 180,000 output tokens per tier. Using the [Haiku 4.5 list price](https://www.anthropic.com/claude/haiku) of $1/$5 per million input/output and [Sonnet 5 list price](https://www.anthropic.com/news/claude-sonnet-5) of $2/$10, the estimated maximum base token charge is **$1.44 + $2.88 = $4.32**. A 20% planning margin is $5.19, rounded to **$5.20**. Prices were checked on 2026-09-27; confirm the actual provider, model IDs, billing route, rates and any cache/tool/tax charges immediately before a paid run. Do not infer that a subscription CLI session follows API list prices.

Record per response: raw output, prompt/response tokens, wall-clock latency, parse/schema/render failures, missing nodes, state/value/focus/action preservation, styling/host/frame outcomes and estimated billed cost. Report per-arm denominators, failures by cause, median and 95th-percentile latency, median token use, and paired per-scenario outcomes with uncertainty. Five repeats per cell are exploratory; do not claim statistical superiority from this sample. The live run remains blocked until the owner approves its provider, cost ceiling and safety boundary. No paid calls were made in this phase.
