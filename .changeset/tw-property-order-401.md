Rule order now follows Tailwind 4's property order (table from Tailwind 4.3.3, regenerated by `scripts/tw-property-order/extract.mjs`): after the variant order, rules sort by their Tailwind property indices, then more declarations first, then class name. When two utilities on one element set the same property (`p-4 px-2`, `border border-l-4`, `size-4 w-8`, `flex-1 grow-0`), the winner is Tailwind's, whichever class the page used first, in `generateCss`, `@barocss/server` and the browser runtime. The runtime places each rule at its global position across its `<style>` partitions (a partition's `data-category` names the category it was opened for), and side-border utilities (`border-t-4`, `border-x-0`, `border-y` …) get the `borders` category.

- Output order changes: rules now follow Tailwind 4's property order, so for overlapping utilities on one element the winning class can differ from earlier releases (it now matches Tailwind).
- Type change: `RuleKey` widens from `number[]` to `(number | string)[]`, and `ruleSortKey(rule, candidate?)` gains an optional `candidate` parameter; TypeScript code that treats key entries as numbers may no longer compile.
- The runtime's `<style data-category="…">` now names the category a partition was opened for; it can also hold rules of other categories.
