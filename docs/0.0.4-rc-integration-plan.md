# BaroCSS 0.0.4 릴리스 후보 통합 계획

작성일: 2026-09-23  
기준 커밋: `4462645` (`develop`)  
상태: 0.0.4 후보에 Core 회귀 수정과 문서 정정을 통합하고 재검사 중이다. PR 검토와 릴리스 결정은 대기 중이다. 릴리스와 배포는 범위에 포함하지 않는다.

## 2026-09-23 통합 현황

Core, Pulse, Mirror, Ship 변경과 Mirror의 비교 입력 설명 보정을 이 브랜치에 통합했다. 통합 순서는 Core → Pulse → Mirror → Ship → Mirror 문서 보정이다. Guard의 [독립 검증 보고서](verification/0.0.4-rc-review.md)도 포함했다. Guard는 최종 문서 보정 전 코드 조합을 별도 디렉터리에서 검사했다. PM은 문서 보정 뒤 이 통합 브랜치를 다시 검사했다.

- Ship의 `0.0.4` 버전 커밋을 통합했다. 세 패키지의 버전과 packed browser/server의 kit 의존성을 pack 검사에서 대조한다. `workspace:*` 내부 의존성을 쓰므로 lockfile 내용은 바뀌지 않았다.
- Node `22.22.0`, pnpm `9.15.4`: 버전 변경 뒤 `pnpm install --frozen-lockfile` 통과.
- Core의 `generateCssRules`별 `!important` 보존 회귀 수정을 통합했다. 수정 뒤 `pnpm check` 통과: kit 41파일·1,419개, browser 10개, server 2개 테스트. 타입 검사·lint·세 패키지 빌드 통과. browser의 기존 lint 경고 2개는 남아 있다.
- 버전 변경 뒤 `node .github/scripts/check-packages.mjs` 통과: packed `0.0.4` 세 패키지의 exports·타입·CDN 파일·런타임 import·내부 의존성을 확인했다.
- Tailwind 비교는 `4.1.13`에 고정한 선택 표본이다. 수정 뒤 15개 입력 중 CSS 구조 일치 8개, 구조 차이 7개, 빈 BaroCSS 규칙 0개다. 이 표본을 전체 호환율로 쓰지 않는다.
- [draft PR #71](https://github.com/barocss/barocss/pull/71)의 [이전 GitHub CI 실행](https://github.com/barocss/barocss/actions/runs/35808946529)은 고정 lockfile 설치·전체 검사·pack 검사를 통과했다. `!important` 수정 뒤 최신 CI는 다시 확인한다.
- Guard는 Chromium 153에서 선택한 네 입력 `hover:block`, `md:block`, `mask-linear-from-50%`, `inset-ring-2`를 실제 브라우저로 비교했다. 지정한 상태에서 계산 스타일과 필요한 픽셀 결과가 같았다. 재현 방법과 조건은 [독립 검증 보고서](verification/0.0.4-rc-review.md)에 있다. Firefox, WebKit, 다른 테마·조합과 Tailwind 전체 범위는 검사하지 않았다.
- Docs Work가 사이트 홈·가이드의 완전 호환 주장과 Quick Start의 미공개 `bootStart` 예제를 고쳤다. 현재 공개된 npm·CDN `0.0.3`과 검토 중인 `0.0.4`를 구분한다. 후속으로 깨진 사이드바 링크, 사설 `runtime.init()` 예제, 잘못 사용한 `generateCssForClasses` 반환값과 근거 없는 성능 문구도 고쳤다. Docs Work의 내부 링크 266개 검사에서 누락이 없었고, PM 통합 브랜치의 Node 22·pnpm 9에서 `pnpm --filter barocss-docs docs:build`가 통과했다. 큰 JS 청크 경고가 있으나 빌드 오류는 없다. 실제 Pages 워크플로는 실행하지 않았다.
- PM 판정: **0.0.4 후보는 선택한 검증 범위에서 PR 검토 가능**하다. `4.1.13` 전체 호환 또는 완전 호환을 주장하지 않는다. PR 검토와 릴리스 결정은 Baro Mento·Release Manager가 별도로 맡는다. 이 결과만으로 npm 게시를 승인하지 않는다.

실행 기록은 [Core #65](https://github.com/barocss/barocss/issues/65), [Pulse #66](https://github.com/barocss/barocss/issues/66), [Mirror #67](https://github.com/barocss/barocss/issues/67), [Ship #68](https://github.com/barocss/barocss/issues/68)에 있다. 미결 AI UI 방향은 [Discussion #69](https://github.com/barocss/barocss/discussions/69), Tailwind 지원 버전 정책은 [Discussion #70](https://github.com/barocss/barocss/discussions/70)에 둔다.

AI UI의 기술 비교와 평가 기준은 [연구 문서](ai-ui-technology-research.md)에 있다. [PoC Issue 초안](ai-ui-poc-issue-draft.md)은 범위·담당·중복을 확인한 뒤 게시할 수 있다. Researcher는 [Discussion #69 보충 기록](https://github.com/barocss/barocss/discussions/69#discussioncomment-18560506)에 60회 평가 계획과 안전 경계를 남겼다. AI UI PoC는 0.0.4 후보 판정과 별개다.

## 목표와 현재 기준선

목표는 세 패키지를 함께 설치하고 검사할 수 있는 0.0.4 릴리스 후보다. Tailwind 완전 호환은 검증할 목표다. 현재 지원 범위와 호환율은 확정하지 않는다.

첫 비교는 Tailwind CSS **4.1.13**에 고정한다. 이 버전은 현재의 측정 기준이며 공개 지원 선언이 아니다. 완전 호환의 다음 목표 버전으로 **4.3.3**을 제안한다. 2026-09-23에 확인한 [공식 릴리스 목록](https://github.com/tailwindlabs/tailwindcss/releases)에서 4.3.3이 최신 안정 릴리스다. 0.0.4 후보 문서에는 실제로 비교한 버전과 범위만 표시한다. 4.3.3 지원 여부는 별도 비교 결과로 결정한다.

기준 커밋에서 세 패키지의 버전은 0.0.3이었다. 당시 루트 `pnpm check`는 통과했고 코어 테스트 1,387개가 통과했다. 브라우저와 서버 패키지에는 실행되는 `test` 스크립트가 없어 이 결과에 두 패키지의 테스트는 포함되지 않는다. CI는 Node 22와 pnpm 9에서 `pnpm check`를 실행한다. 당시 README의 완전 호환 및 95% 이상 호환 주장은 측정 근거가 없었다.

## 확인된 작업과 차단 항목

2026-09-23 중간 보고 기준:

| 항목 | 현재 결과 | 다음 책임 |
| --- | --- | --- |
| Tailwind 4.1.13 초기 비교 | 기준 코드에서는 입력 15개 중 CSS 구조 일치 8개, 구조 차이 6개, 미지원 1개. Mirror의 `mask`·`inset-ring` 수정 뒤 임시 Core 결합에서는 일치 8개, 차이 7개, 빈 규칙 0개다. 이 표본을 전체 호환율로 쓰지 않는다. | Mirror가 차이의 렌더링 영향을 정리하고 통합 트리에서 비교를 다시 실행한다. |
| 패키지 export | pack 검사에서 kit `theme/default` 선언 경로, browser UMD require 경로, server CJS require 경로가 잘못됨을 확인했다. | Ship은 kit 경로를, Pulse는 browser/server 경로를 수정하고 Ship이 pack 검사를 다시 실행한다. |
| 타입 사용 | NodeNext 사용 검사에서 browser의 `BrowserRuntime` 타입 노출이 실패했다. | Pulse가 타입 출력을 수정하고 Ship이 설치 사용 검사를 다시 실행한다. |

이 표의 결과는 개별 작업 트리의 중간 보고다. 통합 완료와 후보 통과를 뜻하지 않는다.

현재 호환성 수정 우선순위는 `mask-linear-from-50%` 미지원, `hover:block`의 hover 조건 누락, `inset-ring-2`의 색·변수 차이다. 초기 `md:block` fixture는 BaroCSS 쪽에만 `768px`을 명시해 Tailwind의 `48rem`과 다른 입력을 비교했다. 양쪽을 `48rem`으로 맞춘 뒤 임계값 차이는 관측되지 않았고 쿼리 문법·중첩 형태 차이만 남았다. `p-4`, `-mt-4`, `focus:block`의 표기·변수 참조 차이도 기록하되 실제 렌더링 영향으로 판단한다.

`mask-linear-from-50%`와 `inset-ring-2`는 Mirror가 `effects.ts`에서 수정한다. `hover:block`은 코어 modifier가 selector와 at-rule을 함께 적용해야 한다. Core가 `engine.ts`와 `registry.ts`의 인터페이스를 맡고 Mirror가 비교 fixture로 결과를 확인한다.

Baro Researcher는 AI 기반 UI 생성 기술과 2주 PoC를 별도 작업 트리에서 조사한다. 연구 결과는 0.0.4 후보의 코드 통합이나 후보 통과 조건에 포함하지 않는다.

각 Work는 독립 작업 트리를 쓴다. 담당 파일이 겹치면 편집 전에 Baro PM과 상대 Work에 알린다. 남의 변경을 되돌리지 않는다.

## 진행 순서

1. **기준 고정:** Mirror는 Tailwind 기준 버전과 비교 범위를 기록한다. Core와 Pulse는 결함을 재현하는 테스트를 먼저 만든다. Ship은 현재 패키지 산출물과 문서 경로를 검사한다.
2. **개별 검증:** 각 Work는 변경 파일 목록, diff 요약, 실행 명령, 결과, 남은 위험을 PM에게 보낸다. 실패한 테스트도 숨기지 않고 재현 방법을 보낸다.
3. **통합 검토:** PM은 Core, Pulse, Mirror, Ship 순서로 변경을 검토한다. 각 변경 뒤 영향을 받는 패키지 테스트를 다시 실행한다. 최종 통합 뒤 전체 검사를 실행한다. 이 순서는 의존 관계에 따라 조정할 수 있다.
4. **후보 판정:** 아래 기준을 모두 확인한다. 미해결 호환 차이나 공개 API 변경이 있으면 Baro Mento에게 근거와 선택지를 보낸다. 후보 판정은 실제 릴리스나 게시를 뜻하지 않는다.

## 릴리스 후보 검증 기준

| 항목 | 통과 기준 | 필요한 증거 |
| --- | --- | --- |
| 변경 범위 | 각 Work의 diff가 담당 범위와 맞고, 예상하지 못한 파일 변경과 충돌이 없다. | 기준 커밋 대비 파일 목록과 diff 검토 기록 |
| 코어 상태 | 서로 다른 설정의 컨텍스트가 registry, cache, prefix 또는 실패 결과를 공유하지 않는다. 재현 테스트와 기존 코어 테스트가 통과한다. | 회귀 테스트 이름, 실행 명령, 결과 |
| 브라우저·서버 | 두 패키지의 `test` 스크립트가 루트 `pnpm test`에서 실행된다. DOM 변경, CSS 캐시, `updateConfig`, `destroy`, 빈 서버 입력의 회귀 테스트가 통과한다. | 세 패키지의 테스트 실행 로그 |
| Tailwind 비교 | Tailwind 기준 버전과 입력 집합을 고정한다. 같은 입력에서 생성한 CSS를 정규화한 뒤 비교하고, 차이의 입력·출력·원인을 기록한다. | 재현 가능한 비교 명령, fixture 목록, 차이 보고서 |
| 호환 주장 | 문서의 지원 범위와 수치가 비교 결과와 일치한다. 측정하지 않은 완전 호환 또는 호환율은 표시하지 않는다. | 비교 결과와 수정된 문서 diff |
| 타입·정적 검사 | 통합된 코드에서 `pnpm check`가 통과한다. CI의 Node 22와 pnpm 9 조합에서도 통과한다. | 로컬 결과와 CI 결과 |
| 패키지 사용 | 세 패키지를 빌드하고 pack 산출물에서 공개 import, 타입, ESM/CJS 경로와 브라우저 CDN 파일을 검사한다. 문서 예제의 import가 실제 산출물에서 동작한다. | 빌드·pack 파일 목록과 설치 사용 검사 결과 |
| 버전 정합성 | 후보 산출물의 세 패키지 버전과 내부 의존성, lockfile이 서로 맞는다. | package 파일 및 lockfile diff |

호환 비교에서 차이가 나오면 Mirror가 범위와 심각도를 기록한다. 기능에 영향이 있는 미해결 차이는 후보 판정을 보류한다. 단순 비교 형식 차이는 CSS 의미가 같은 근거를 기록한다. 판정 기준을 바꿀 때는 Baro Mento에게 먼저 보고한다.

## 보고 형식

각 Work는 **완료 / 진행 중 / 막힘** 중 하나로 상태를 보낸다. 보고에는 담당 범위, 변경 커밋 또는 diff, 통과·실패한 검사, 다른 Work에 필요한 작업, 남은 위험을 넣는다. PM은 이를 한 목록으로 정리해 Baro Mento에게 우선순위와 후보 판정 상태를 전달한다.

GitHub에서는 Issue에 실행 단위·담당·수용 기준·테스트·결과 링크를 둔다. 미결 설계와 연구는 Discussion에 두고, 확정된 구조·지원 범위·운영 절차만 Wiki에 기록한다. Discussion에서 결정한 실행 작업은 Issue에 연결한다. 완료 Issue에는 검증 근거와 Wiki 갱신 여부를 남긴다. PM이 중복과 게시 내용을 최종 확인한다.
