# GPU 기능 로드맵

기준일: 2026-10-27. 목표는 브라우저의 3D 장면을 구성하고 표시하는 데 필요한 기능을 단계적으로 늘리는 것이다. Three.js의 전체 기능과 API가 이미 지원된다는 뜻은 아니다. 각 번호는 구현 범위와 검증 결과가 확인될 때 완료로 바꾼다. 현재 목록은 첫 실행 계획이며, 전체 기능의 최종 개수나 완료율은 아니다.

## 현재 위치

| 범위 | 현재 상태와 한계 |
| --- | --- |
| 장면과 조작 | 카메라, orbit, 메시, 인스턴스, rigid transform, 텍스처, 픽킹과 이미지 캡처가 있다. |
| 재질과 조명 | PBR 재질, 환경 조명, directional·point·spot 조명과 제한된 그림자 경로가 있다. 광원 수와 그림자 방식에는 제한이 있다. |
| 후처리 | 색상 보정, bloom, DoF 등이 있다. 모든 Three.js 효과를 지원하는 것은 아니다. |
| 고정 이미지 경로 추적 | BVH, 누적, denoise, 고정 snapshot과 직접 조명이 있다. clip/cap과 raster 후처리는 지원 범위 밖이다. |
| 최근 완료 | `fe2637f411f31b416bb204bec4f812615a13d466`에서 point·spot의 양수 반경을 경로 추적 그림자 가림에 연결했다. 새 CPU 시험 8개, 실제 GPU 브라우저 시험 1개와 공개 예제 확인을 통과했다. 이 기능은 원판의 가림을 표본화하며 완전한 area-light 방사 적분은 아니다. |

위 결과는 소유 branch의 검증 범위다. 제품 병합과 제품 품질 인수는 별도로 기록한다.

## 앞으로 할 일

| 번호 | 상태 | 작업 | 완료 기준 |
| --- | --- | --- | --- |
| 01 | 다음 | 공개 RenderTarget 기초. 현재 canvas와 같은 크기·출력 형식의 단일 색상 대상에 렌더하고 읽는다. 기존 중간 color/depth 경로를 재사용한다. | 대상별 픽셀, 반복 사용, 다른 viewer의 대상 거부, resize 불일치, dispose와 device loss를 새 시험으로 확인한다. 실제 브라우저 예제와 PNG를 남긴다. |
| 02 | 예정 | RenderTarget의 독립 크기와 텍스처 소비를 지원한다. 카메라 비율, 중간 버퍼와 후처리의 대상 크기를 함께 분리한다. | 서로 다른 크기 두 대상의 픽셀과 resize·수명·재질 샘플링을 확인한다. 기존 canvas 출력과 픽킹의 영향도 확인한다. |
| 03 | 부분 완료 | 정적 glTF/GLB를 가져온다. 삼각 메시, 노드 변환과 기본 재질·텍스처부터 시작한다. | 알려진 파일의 구조, 변환 수치와 실제 픽셀을 확인한다. 지원하지 않는 입력과 자원 해제를 명시한다. |
| 03.1 | 소유 branch 완료 | `5d8b77579fe65fff331e878d657e78e0fcbe7519`에서 self-contained GLB 삼각형, 노드 변환과 불투명 기본 PBR factor를 viewer 입력으로 변환한다. | 수정 후 emit, 새 CPU 시험 18개, lint와 합성 샘플의 실제 브라우저 자동 로드·재로드를 확인했다. 외부 asset 인수와 texture·animation·skin·morph 지원은 남는다. |
| 04 | 예정 | 실제 glTF 사용 사례에서 확인된 재질, 텍스처, 여러 메시와 확장 기능의 차이를 순서대로 줄인다. | 각 차이마다 입력 파일, 기대 결과, 실패 방식과 브라우저 이미지를 남긴다. |
| 05 | 예정 | Morph position target과 weight를 추가한다. | weight 0의 원본 보존, 변형 수치, bounds, pick과 고정 PT snapshot을 확인한다. |
| 06 | 예정 | 공개 cube texture 환경 입력을 추가한다. 기존 equirectangular 환경 입력을 유지한다. | 여섯 면의 순서와 방향, 색 공간, 수명 및 실제 반사 이미지를 확인한다. |
| 07 | 예정 | 재질·텍스처 지원 범위를 실제 사용 사례와 비교하고 빠진 조각을 추가한다. | 지원 표와 입력별 기대 픽셀, 오류와 자원 해제를 기록한다. 기존 기능을 미구현으로 다시 만들지 않는다. |
| 08 | 예정 | 조명·그림자의 품질과 남은 광원 기능을 확장한다. 현재 PCSS와 PT의 근사 범위를 구분한다. | 기준 장면에서 광원별 결과를 비교한다. 새 기능마다 독립 픽셀 시험과 브라우저 이미지를 남긴다. |
| 09 | 예정 | 비동기 GPU 결과의 최신성 및 수명 경계를 점검한다. 카메라, 객체, clip, 요청과 device 변경 중 남은 사례를 먼저 재현한다. | 확인된 실패의 원문을 보존하고, 최소 수정 뒤 해당 경로만 재검증한다. |
| 10 | 예정 | G15 엔진 still과 turntable을 실제 사진과 비교한다. | 소유 branch 증거, 제품 채택과 사용자의 품질 판단을 따로 기록한다. 한 장면의 통과를 전체 품질 인수로 확대하지 않는다. |
| 11 | 조건부 | 성능과 temporal accumulation을 검토한다. 먼저 실제 장면에서 비용과 효과를 측정한다. | 측정 조건과 결과를 기록한다. G14 측정은 `load < 10`에서만 한다. 이득과 비용을 확인한 경우에만 temporal을 선택한다. |
| 12 | 조건부 | Skin과 character animation을 추가한다. 먼저 asset 제공 경로, consumer, 소유자와 시간·root motion 기준을 정한다. | 작은 skeleton의 pose와 변형 수치, bounds·pick·PT 경계를 확인한다. 기존 Motion 작업의 보류 조건을 유지한다. |
| 13 | 조건부 | LOD, 새 BVH 또는 culling을 검토한다. | 실제 workload와 정확성·자원 예산을 먼저 확보한다. 근거가 있는 병목부터 수정하고 측정한다. |
| 14 | 예정 | Three.js의 장면·재질·조명·애니메이션·입출력 기능을 사용 사례별로 대조한다. | 지원, 부분 지원, 미지원과 명시적 제외를 표로 유지한다. 새로운 차이는 다음 번호로 추가한다. |

번호 01부터 순서대로 진행한다. 09와 10의 조사처럼 독립적인 읽기 작업은 병렬로 할 수 있다. 실제 GPU·브라우저 실행은 다른 레인과 겹치지 않게 조정한다. 기존 통과 검사는 반복하지 않는다. 새 실패는 원문과 이미지를 보존하고 수정한 경로를 다시 검증한다. 각 작업은 소유 branch에 정상 commit하고 결과를 보고한다. 제품 병합은 별도 담당이 수행한다.
