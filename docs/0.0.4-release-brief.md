# BaroCSS 0.0.4 release brief

## 결정 상태

**현재 판정: PR #71 병합과 게시 보류.** [PM의 릴리스 게이트](https://github.com/barocss/barocss/pull/71#issuecomment-5789060900)에 따라 `BrowserRuntime.removeClass()`의 CSS 제거 계약을 수정하고 검증해야 한다. [Guard는 HEAD `6df9af9`에서 CSS 규칙이 남는 결함을 재현했다](https://github.com/barocss/barocss/pull/71#issuecomment-5789086489). 이 HEAD의 [GitHub CI](https://github.com/barocss/barocss/actions/runs/35811988706)는 성공했지만, 해당 동작은 검사하지 못했다. Pulse의 #71 기준 수정, Guard 독립 재검증, PM의 통합 판정이 필요하다. 그 뒤에도 릴리스 자동화 변경 병합, npm 인증 확인, `npm` 환경의 승인 규칙 설정, 게시 결정이 남는다.

## 현재 절차의 위험

`release.yml`은 수동 `workflow_dispatch`에서 Changesets publish를 활성화한다. 원래 설정에는 실행 브랜치 제한과 게시 버전 확인이 없다. PR #71은 `pnpm check`와 pack 검사를 추가했지만, 0.0.4 버전을 직접 올렸고 대기 중인 changeset은 없다. 따라서 기존 워크플로를 후보 브랜치에서 실행하면 병합 전에 0.0.4가 게시될 수 있다.

`develop` 보호 설정은 Code Owner 승인 1건을 요구한다. CI 상태 검사의 필수 context는 비어 있고 관리자 우회도 허용한다. CI 성공을 별도로 확인해야 한다. 저장소 Actions 기본 토큰 권한은 read이며, 기존 `release.yml`의 job 권한에는 `pull-requests: write`가 없다. 이 상태에서 Changesets가 버전 PR을 만들 수 있다고 가정하지 않는다.

공개 browser 0.0.3은 CommonJS `require` 경로를 표시하지만, 별도 Node 22 소비자에 설치해 `require('@barocss/browser')`를 실행하면 kit의 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 실패한다. 0.0.4는 이 경로를 제거하고 ESM import를 지원 경로로 명시한다. 기존 사용자가 CJS 경로를 기대했다면 변경을 알려야 한다.

이 브랜치의 자동화 변경은 기존 파일을 **버전 PR 전용**으로 바꾸고, 새 `npm-release.yml`에 별도 게시 경로를 둔다. 두 작업 모두 `develop`에서만 실행한다. 게시 워크플로는 `publish=false`가 기본값이고 세 패키지 버전, 대기 중인 changeset, 전체 검사, pack 검사를 확인한다. `publish=true`를 선택할 때만 Changesets가 npm 게시, 태그, GitHub Releases를 처리한다. 게시 작업은 `npm` 환경을 사용한다. **현재 BaroCSS에는 그 환경이 없다.** 환경을 만들고 필수 검토자 규칙을 설정하기 전에는 승인 게이트가 작동하지 않는다.

## 버전 규칙과 릴리스 순서

세 패키지는 `.changeset/config.json`의 `linked` 그룹이다. `baseBranch`는 `develop`, 내부 의존성 갱신 방식은 `patch`, 공개 범위는 `public`이다. 이 그룹에서는 변경을 기록한 패키지와 의존 패키지가 같은 목표 버전을 갖는지 최종 결과로 확인한다. Changesets의 linked 설정만으로 모든 패키지가 항상 자동으로 올라간다고 가정하지 않는다.

**0.0.4 예외:** PR #71은 이미 버전과 lockfile을 0.0.4로 올렸다. 이 변경에 지금 patch changeset을 더해 `changeset version`을 실행하면 0.0.5가 될 수 있다. 따라서 0.0.4에는 새 version PR을 만들지 않는다. PR #71의 변경 내역과 Guard 보고서를 0.0.4 release notes의 근거로 쓴다.

**다음 릴리스부터:** 변경 PR마다 영향 패키지와 `patch`/`minor`/`major`를 명시한 changeset을 추가한다. `develop` 병합 뒤 **Npm version PR**을 수동 실행한다. 생성된 `changeset-release/develop` PR의 버전, 세 `CHANGELOG.md`, 내부 의존성, lockfile을 검토하고 CI 통과 후 병합한다. 그런 다음 **Npm release**를 `publish=false`로 실행해 준비 결과를 확인한다. 게시 승인 뒤 같은 `develop` 커밋에서 `publish=true`를 실행한다. 버전 정책을 바꿀 때는 PM이 세 패키지의 공개 API 영향과 0.x 변경 의미를 문서로 결정한다.

## Go / No-go

Go는 `removeClass()` 계약 수정과 Guard의 독립 재검증이 통과하고, PR #71과 자동화 PR이 모두 병합되고, 최신 `develop` CI·사이트 빌드·링크 검사·dry-run이 성공하고, PM이 Guard의 제한된 검증 범위 및 아래 릴리스 노트를 승인하고, npm 인증과 환경 승인 규칙이 확인되고, 사용자가 실제 게시를 승인할 때만 가능하다. 하나라도 빠지면 No-go다. PM은 제품 범위, Release Manager는 실행 증거, Mento는 게시 결정을 확인한다. 한 사람이 판단을 대신하지 않는다.

## 실패와 사후 확인

- **게시 전 실패:** 워크플로를 멈춘다. 코드와 버전을 고친 새 PR을 만들고 CI·dry-run을 다시 실행한다.
- **일부 패키지만 게시:** 세 npm 버전을 먼저 조회하고 결과를 기록한다. 이미 게시한 버전은 재게시하지 않는다. 실패 원인을 고친 뒤 같은 버전의 남은 패키지만 게시할 수 있는지 검토한다. 자동 재실행은 하지 않는다.
- **태그 또는 Release만 누락:** npm 게시 결과와 실제 커밋을 확인한 뒤 누락 기록을 복구한다. 게시 실패를 GitHub Release 성공으로 보고하지 않는다.
- **0.0.4 결함:** 영향을 받은 0.0.4에 npm deprecate 안내를 붙이고 수정한 patch 버전을 새로 낸다. 이미 배포된 0.0.4를 되돌리거나 같은 번호로 덮어쓰는 절차를 계획하지 않는다.
- **게시 후 24시간:** npm 설치, 패키지별 import/require/타입, browser CDN 경로, 세 Releases·태그, 관련 Issue와 오류 보고를 확인한다. PM이 고객 안내 필요 여부를 정한다.

## Release notes 초안

**BaroCSS 0.0.4**는 kit의 Context 상태 격리, 클래스별 `!important` 처리, 중복되거나 중첩된 `@property` 출력 수정, browser의 DOM 변경·설정 갱신·종료 처리, server의 빈 입력 처리를 개선한다. 세 패키지의 배포 export·타입·라이선스 파일을 점검했고, browser와 server 테스트를 루트 검사에 포함했다. browser는 ESM import를 사용한다. 0.0.3에 표시됐지만 동작하지 않던 CommonJS `require` 경로는 제거했다. 선택한 Tailwind CSS 4.1.13 입력은 고정 fixture와 Chromium 렌더링으로 비교했다. 이 검사는 Tailwind 전체 호환성 보증이 아니다. API 또는 설치 방식에 영향을 주는 변경은 PR #71의 최종 diff와 패키지 README를 기준으로 게시 직전에 다시 확인한다.

## barocss-editor와의 차이 및 준비 작업

[barocss-editor의 버전 PR](https://github.com/barocss/barocss-editor/blob/main/.github/workflows/npm-version.yml)은 `main`에서 Changesets version PR을 만든다. [npm 릴리스](https://github.com/barocss/barocss-editor/blob/main/.github/workflows/npm-release.yml)는 기본 검사 모드, `npm` 환경, pack 및 격리된 소비자 검사, 선택형 trusted/bootstrap 인증을 쓴다. BaroCSS의 이 변경은 같은 **버전 PR → 검사 전용 실행 → 승인된 게시** 순서를 마련하지만, 현재 게시 인증은 기존 `NPM_TOKEN`이다. editor의 npm 환경도 API상 required reviewer 규칙이 비어 있으므로, 이름만으로 승인 게이트가 있다고 보지 않는다.

BaroCSS가 editor 수준의 tarball 재사용과 npm OIDC trusted publishing으로 옮기려면 npm의 세 패키지에 이 저장소·워크플로를 trusted publisher로 등록하고, npm CLI 및 pnpm 게시 동작을 검증하고, tarball을 검사한 그대로 게시하는 스크립트와 CI 소비자 검사를 추가해야 한다. 이는 별도 변경으로 검증한다. 이번 0.0.4 게시의 필수 조건은 현재 토큰 방식의 권한·승인·dry-run 확인이다.

설정 순서는 다음과 같다.

1. GitHub 저장소의 **Settings → Environments**에서 `npm`을 만든다. required reviewer와 `develop` 배포 브랜치 제한을 설정한다. 현재 `barocss-editor`의 `npm` 환경에도 required reviewer는 없으므로, 그 설정을 그대로 복사하지 않는다.
2. **Settings → Branches**에서 `develop`의 `Test and Build`를 필수 검사로 지정한다. 지금은 필수 검사 목록이 비어 있다. 버전 PR을 자동 생성하려면 Actions의 PR 생성 허용 설정도 유지한다.
3. 첫 0.0.4 릴리스는 기존 `NPM_TOKEN`을 사용한다. `publish=true` 실행은 먼저 `npm whoami`로 토큰 유효성을 확인한다. 세 패키지 게시 권한과 npm의 2FA 정책은 저장소 설정만으로 확인할 수 없으므로 담당자가 npm에서 확인한다.
4. 이후 토큰을 없애려면 각 패키지의 npm **Trusted Publisher**에 GitHub 조직 `barocss`, 저장소 `barocss`, 워크플로 파일 `npm-release.yml`, 환경 `npm`을 등록한다. 직접 `npm publish`를 허용한다. [npm 공식 문서](https://docs.npmjs.com/trusted-publishers/)는 Node 22.14 이상과 npm CLI 11.5.1 이상을 요구한다. 현재 Changesets·pnpm 게시 명령이 OIDC로 동작하는지 별도 검증한 뒤 `NPM_TOKEN` 사용을 제거한다.
