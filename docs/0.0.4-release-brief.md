## 현재 절차의 위험

초기 `release.yml`은 수동 `workflow_dispatch`에서 Changesets publish를 허용했다. #73은 이 파일을 버전 PR 전용으로 바꾸고 `npm-release.yml`을 검사 전용으로 만들었다. 이 PR #77은 게시 경로를 `main`의 승인된 승격 커밋과 CI에만 연결한다. 0.0.4 버전은 #71에서 직접 올렸고 대기 중인 changeset은 없다.

`develop` 보호 설정은 PR과 최신 `Test and Build` 검사를 요구한다. 승인 리뷰와 Pages 배포는 필수가 아니다. 저장소 Actions 기본 토큰 권한은 read이며, 기존 `release.yml`의 job 권한에는 `pull-requests: write`가 없다. 이 상태에서 Changesets가 버전 PR을 만들 수 있다고 가정하지 않는다.

공개 browser 0.0.3은 CommonJS `require` 경로를 표시하지만, 별도 Node 22 소비자에 설치해 `require('@barocss/browser')`를 실행하면 kit의 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 실패한다. 0.0.4는 이 경로를 제거하고 ESM import를 지원 경로로 명시한다. 기존 사용자가 CJS 경로를 기대했다면 변경을 알려야 한다.

이 브랜치의 자동화 변경은 기존 파일을 **버전 PR 전용**으로 바꾼다. PM이 준비를 확인한 정확한 `develop` SHA와 버전을 **Npm promotion**에 지정하면, 검증 뒤 그 커밋의 고정 브랜치로 `main` PR을 만든다. `main`의 독립 승인과 `build`·`test`가 끝나야 일반 auto-merge가 작동한다. 병합된 `main` 커밋에서 CI가 다시 성공한 뒤 **Npm release**가 게시한다. 수동 실행은 검사와 npm 인증 확인만 하며 게시하지 않는다. **현재 BaroCSS에는 `npm` 환경이 없다.** 환경에 `main` 제한, 활성화 변수, 토큰을 설정하기 전에는 게시가 중단되어야 한다. 자세한 조건은 [자동 릴리스 설계](automatic-release.md)에 있다.

## 버전 규칙과 릴리스 순서

세 패키지는 `.changeset/config.json`의 `linked` 그룹이다. `baseBranch`는 `develop`, 내부 의존성 갱신 방식은 `patch`, 공개 범위는 `public`이다. 이 그룹에서는 변경을 기록한 패키지와 의존 패키지가 같은 목표 버전을 갖는지 최종 결과로 확인한다. Changesets의 linked 설정만으로 모든 패키지가 항상 자동으로 올라간다고 가정하지 않는다.

**0.0.4 예외:** PR #71은 이미 버전과 lockfile을 0.0.4로 올렸다. 이 변경에 지금 patch changeset을 더해 `changeset version`을 실행하면 0.0.5가 될 수 있다. 따라서 0.0.4에는 새 version PR을 만들지 않는다. PR #71의 변경 내역과 Guard 보고서를 0.0.4 release notes의 근거로 쓴다.

**다음 릴리스부터:** 변경 PR마다 영향 패키지와 `patch`/`minor`/`major`를 명시한 changeset을 추가한다. `develop` 병합 뒤 **Npm version PR**을 수동 실행한다. 생성된 `changeset-release/develop` PR의 버전, 세 `CHANGELOG.md`, 내부 의존성, lockfile을 검토하고 CI 통과 후 병합한다. Guard·Ship 근거와 설정 검증이 끝나면 PM은 정확한 `develop` SHA와 버전으로 준비 기록을 남기고 **Npm promotion**을 실행한다. 그 뒤의 `main` 병합과 npm 게이트는 [자동 절차](automatic-release.md)를 따른다. 버전 정책을 바꿀 때는 PM이 세 패키지의 공개 API 영향과 0.x 변경 의미를 문서로 결정한다.

## Go / No-go

PR #71과 #73의 통합은 완료됐다. Go는 #77의 최종 통합, 정확한 `develop` SHA의 CI·사이트 빌드·pack·npm 충돌 검사, GitHub App과 npm 환경·게시 권한 확인, Guard·Ship 근거, PM의 SHA·버전 준비 기록이 모두 있어야 가능하다. 사용자는 이 조건부 자동 절차를 승인했다. `main` PR에는 `easylogic`의 독립 승인과 필수 `build`·`test`가 필요하다. 하나라도 빠지면 No-go다.

## 실패와 사후 확인

- **게시 전 실패:** 워크플로를 멈춘다. 코드와 버전을 고친 새 PR을 만들고 CI·dry-run을 다시 실행한다.
- **일부 패키지만 게시:** 세 npm 버전을 먼저 조회하고 결과를 기록한다. 이미 게시한 버전은 재게시하지 않는다. 실패 원인을 고친 뒤 같은 버전의 남은 패키지만 게시할 수 있는지 검토한다. 자동 재실행은 하지 않는다.
- **태그 또는 Release만 누락:** npm 게시 결과와 실제 커밋을 확인한 뒤 누락 기록을 복구한다. 게시 실패를 GitHub Release 성공으로 보고하지 않는다.
- **0.0.4 결함:** 영향을 받은 0.0.4에 npm deprecate 안내를 붙이고 수정한 patch 버전을 새로 낸다. 이미 배포된 0.0.4를 되돌리거나 같은 번호로 덮어쓰는 절차를 계획하지 않는다.
- **게시 후 24시간:** npm 설치, 패키지별 import/require/타입, browser CDN 경로, 세 Releases·태그, 관련 Issue와 오류 보고를 확인한다. PM이 고객 안내 필요 여부를 정한다.

## Release notes 초안

**BaroCSS 0.0.4**는 kit의 Context 상태 격리, 클래스별 `!important` 처리, 중복되거나 중첩된 `@property` 출력 수정, browser의 DOM 변경·설정 갱신·종료 처리, server의 빈 입력 처리를 개선한다. 세 패키지의 배포 export·타입·라이선스 파일을 점검했고, browser와 server 테스트를 루트 검사에 포함했다. browser는 ESM import를 사용한다. 0.0.3에 표시됐지만 동작하지 않던 CommonJS `require` 경로는 제거했다. 선택한 Tailwind CSS 4.1.13 입력은 고정 fixture와 Chromium 렌더링으로 비교했다. 이 검사는 Tailwind 전체 호환성 보증이 아니다. API 또는 설치 방식에 영향을 주는 변경은 PR #71의 최종 diff와 패키지 README를 기준으로 게시 직전에 다시 확인한다.

## barocss-editor와의 차이 및 준비 작업

[barocss-editor의 버전 PR](https://github.com/barocss/barocss-editor/blob/main/.github/workflows/npm-version.yml)은 `main`에서 Changesets version PR을 만든다. [npm 릴리스](https://github.com/barocss/barocss-editor/blob/main/.github/workflows/npm-release.yml)는 기본 검사 모드, `npm` 환경, pack 및 격리된 소비자 검사, 선택형 trusted/bootstrap 인증을 쓴다. BaroCSS는 **버전 PR → PM이 고정 SHA 지정 → 보호된 `main` 승격 → `main` CI 뒤 npm 게시** 순서를 마련한다. 현재 인증은 기존 `NPM_TOKEN`이다.

BaroCSS가 editor 수준의 tarball 재사용과 npm OIDC trusted publishing으로 옮기려면 npm의 세 패키지에 이 저장소·워크플로를 trusted publisher로 등록하고, npm CLI 및 pnpm 게시 동작을 검증하고, tarball을 검사한 그대로 게시하는 스크립트와 CI 소비자 검사를 추가해야 한다. 이는 별도 변경으로 검증한다. 이번 0.0.4 게시의 필수 조건은 현재 토큰 방식의 권한·승인·dry-run 확인이다.

설정 순서는 다음과 같다.

1. GitHub App을 이 저장소에 설치한다. Metadata read, Administration read, Contents write, Pull requests write를 부여한다. 저장소 변수 `BARO_PROMOTION_APP_CLIENT_ID`와 비밀 `BARO_PROMOTION_APP_PRIVATE_KEY`를 설정한다. App에는 보호 규칙 우회 권한을 주지 않는다.
2. GitHub 저장소의 **Settings → Environments**에서 `npm`을 만들고 `main`만 허용한다. 환경 변수 `NPM_RELEASE_ENABLED=true`와 환경 비밀 `NPM_TOKEN`을 설정한다. 기존 저장소 비밀은 환경으로 옮긴 뒤 제거한다. 매번 사람 승인을 요구하는 reviewer 규칙은 조건부 자동 게시 정책에 넣지 않는다.
3. `main`의 독립 승인 1건과 필수 `build`·`test`를 유지한다. 이 브랜치의 CI 변경을 통해 해당 이름의 검사를 실행한다. `develop`은 PR과 최신 `Test and Build`가 필수다.
4. 첫 0.0.4 릴리스는 `NPM_TOKEN`을 사용한다. 게시 직전 `npm whoami`로 로그인 상태를 확인한다. 세 패키지 게시 권한과 npm 2FA 정책은 담당자가 npm 설정에서 확인한다. 이후 OIDC로 옮기려면 각 패키지의 npm **Trusted Publisher**에 GitHub 조직 `barocss`, 저장소 `barocss`, 워크플로 파일 `npm-release.yml`, 환경 `npm`을 등록한다. [npm 공식 문서](https://docs.npmjs.com/trusted-publishers/)는 Node 22.14 이상과 npm CLI 11.5.1 이상을 요구한다. Changesets·pnpm 게시 명령의 OIDC 동작을 별도 검증한 뒤 토큰을 제거한다.
