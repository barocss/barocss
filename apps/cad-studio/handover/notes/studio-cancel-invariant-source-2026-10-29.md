## Finding

The global invariant **“no unrelated accepted document mutation can occur while the work controlled by Stop is pending” is not established; the Render settings path permits such a mutation in source.** This is stronger than merely noticing `doUndo`, but remains a scheduling hypothesis until a bounded actual UI run observes the required interval.

The narrow candidate is an ordinary committed model evaluation (not a parameter candidate, preview-only computation or repair stage), followed by a Render/Scene settings edit while `busy && slow` stays true, then Stop. Source has no busy guard on that Render edit; its document commit adds an Undo entry without changing the model memo or stopping the existing evaluation. Stop takes the current top Undo entry rather than a recorded operation identity. No runtime wrong-Undo or data-loss defect is asserted here.

## Why a Render-only commit can leave the original Stop active

The source deliberately excludes render settings from model reevaluation. In a nonvariant master, `useVariants` returns `shown:doc`: [useVariants.ts:34](/Users/user/Documents/ChatGPT/barocss/.omx/research/cad-commercial-readiness-20261029/runtime/5463dbf32/apps/cad-studio/src/state/useVariants.ts:34), B34–47. The model memo depends on nodes, parameters, frame sections, content key, relevant followed parts and marker: [App.tsx:783](/Users/user/Documents/ChatGPT/barocss/.omx/research/cad-commercial-readiness-20261029/runtime/5463dbf32/apps/cad-studio/src/App.tsx:783), B783–795. `contentKey` includes model/shop/bearing inputs but no render or drawing field: [evalMemo.ts:61](/Users/user/Documents/ChatGPT/barocss/.omx/research/cad-commercial-readiness-20261029/runtime/5463dbf32/packages/barocss-cad-model/src/engine/evalMemo.ts:61), B61–66. Thus a render-only shallow document update retains the memo dependencies for this simple master case. The main effect dependencies are engine/evaluated/parameterEdit/parameterCurrent (App921), also unchanged when no parameter candidate is active.

This is not a claim that every appearance edit preserves every model key. The proposed fixture excludes variability, bearing dependencies, followed assembly frames and parameter candidates. It uses a render environment flag with unchanged node/parameter/instance references.

## Smallest pending runtime schedule

Let D0 be the accepted master model, D1 the newly committed expensive model change, and D2=D1 plus one Render environment change.

1. Commit one actual supported expensive feature from D0 to D1. Record document nodes, Undo identity/depth, active worker request and its source/revision. Wait until the existing Stop work bar is visible (`busy && slow`, no `stage`). The chosen cold workload must remain pending long enough for the next two user actions; finding that workload is **NOT_RUN**.
2. Click Render→Scene; toggle Grid once. Verify D2 is accepted (`doc.render.environment.grid` changed, dirty true), node/parameter references unchanged, the D1 worker is still pending, and the same Stop remains visible. This observation is the key runtime prerequisite; a screenshot alone cannot show it.
3. Click Stop. The inspected stack semantics predict one pop restores D1, removing the newer Render edit while leaving D1's model change in the document. This is a **source-derived prediction**, not an executed result. The required acceptance instead is to retain newer independent accepted edits while cancelling only the originating computation, or to prevent those edits under a stated busy invariant.
4. Record actual doc/Undo/Redo, dirty/recovery proposal, displayed body source and all resolved pending requests after Stop; then perform one small supported edit and Undo. Do not infer geometry acceptance from stale pixels. A fresh worker should not adopt an old epoch reply.

An injected delayed worker reply could deterministically test the schedule but would prove only controlled scheduling, not the natural workload timing. A natural long computation can qualify the actual UI scheduling. Keep those receipts distinct. Do not modify product source to create the delay. If a runtime probe finds the Render mutation rejected, Stop disappears before commit, or the worker has already completed, preserve that outcome and narrow the schedule rather than declaring a defect.
