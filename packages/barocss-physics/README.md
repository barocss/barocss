# @barocss/physics

A bounded, renderer-neutral fixed-step 3D Physics package. Its rigid world simulates admitted sphere, oriented-box and capsule pairs, limited fixed/hinge joints and narrow opt-in CCD profiles. A separate visual-water world simulates one fixed 256-particle basin. The caller owns time and display. The package does not simulate exact CAD Surface or mesh collision, general joint networks, cloth or engineering fluid flow.

| Entry point | Current result | Example |
| --- | --- | --- |
| `@barocss/physics` | Rigid bodies, contacts, commands, bounded joints and queries | [3D native-Surface Viewer](../../examples/physics-viewer-scene/README.md) |
| `@barocss/physics/cad-proxy` | Admit a labelled sphere or box proxy from one original CAD Surface; map accepted body poses to Viewer | [CAD proxy scene](../../examples/physics-cad-scene/README.md) |
| `@barocss/physics/replay` | Save and validate one bounded accepted command log | [replay probe](../../examples/physics-scene/replay-probe.mjs) |
| `@barocss/physics/fluid` | Simulate and copy 256 visual-water particle positions | [water Viewer scene](../../examples/physics-scene/fluid-viewer/README.md) |
| `@barocss/physics/fluid-cad` | Admit one static CAD-derived box obstacle for version 1 water | [CAD shelf Viewer scene](../../examples/physics-scene/fluid-cad-viewer/README.md) |

Normal Node and package imports use compiled `dist` JavaScript and declarations. A TypeScript-capable workspace bundler can select the `barocss-source` condition to read the matching `src/*.ts` entry without rebuilding Physics. That condition does not make plain Node execute TypeScript. CAD Surfaces remain original display geometry; CAD admission creates a separate sphere or box simulation proxy. See the limits below before using any profile.

The rigid public entry is `src/index.ts`. Types and internal body records are in `types.ts`; input admission is in `validation.ts`; vectors, quaternions and inertia transforms are in `math.ts`; primitive collision and contact response are in `collision.ts`; joint parsing is in `joints.ts`, anchored motor drive is in `joint-motor.ts`, and the two-dynamic-body fixed and hinge profiles are in `dynamic-fixed-joint.ts` and `dynamic-hinge-joint.ts`; CCD admission and sweeps are in `ccd.ts`, `ccd-pair.ts`, `ccd-box.ts` and `ccd-slab.ts`; optional broad-phase bounds are in `broadphase.ts`; large-scene filtering and contact-island sleep rules are in `scene-profile.ts` and `sleep.ts`; and fixed-step world state is in `world.ts`. `limits.ts` holds shared bounds.

The optional `@barocss/physics/fluid` subpath provides a bounded 3D water-particle world. Version 1 admits exactly 256 initial particles in a 0.7 × 1.3 × 0.5 m static basin, gravity `[0,-9.81,0]`, and a caller-driven 1/120 s step. Version 2 keeps that scene and requires the fixed opt-in field `visualViscosity:{kind:'xsph',coefficient:0.15}`. It blends nearby particle velocities after density projection; version 1 behavior and hashes stay unchanged. Initial centres must stay inside the basin with at least 0.025 m spacing. `createFluidWorld(scene)` returns `step(dt)`, `getState()`, `reset()` and `dispose()`. State contains copied `Float64Array` XYZ metre positions and velocities, stable particle indices, a step count and normalized density diagnostics. The caller owns display and clock. The visual coefficient is not a calibrated material viscosity. No emitter, moving obstacle, rigid coupling or CFD accuracy is claimed. See [FLUID-01 #813](https://github.com/barocss/barocss/issues/813), [FLUID-03 #815](https://github.com/barocss/barocss/issues/815) and the [solver decision](../../examples/physics-fluid-spike/README.md).

The opt-in `@barocss/physics/fluid-cad` subpath binds a version 1 fluid scene to one admitted static box derived from a BaroCAD sourceVersion 0 native Surface. `createCadFluidWorld(scene, sourceText, request)` accepts a static `box` CAD proxy inside the basin, with no initial particle overlap. The obstacle uses the CAD proxy's metre centre and half extents, expanded by the particle radius. `step(dt,{sourceText,currentRevision})` and `reset({sourceText,currentRevision})` check the exact source text and revision before changing state. A stale source throws `STALE_SOURCE` and retains the last accepted state. `getObstacle()` returns copied source identity, body ID, box dimensions and the approximation label. State adds per-step `obstacleHits`; this is a projection count, not a force or pressure. The first profile admits one fixed axis-aligned box and version 1 water only. It does not resolve the exact CAD Surface, swept thin features, moving obstacles or v2 visual settling together with CAD. See [FLUID-04 #816](https://github.com/barocss/barocss/issues/816) and the [CAD water example](../../examples/physics-scene/fluid-cad-viewer/README.md).

The bounded fluid neighbor grid uses reusable numeric cell arrays for the declared basin and two sampled floor layers. It visits cells and particle indices in the same order as the original string-key grid, so the frozen v1, v2 and CAD shelf position hashes stay unchanged. The measured browser playback and its machine limits are recorded in [FLUID-05a #871](https://github.com/barocss/barocss/issues/871) and the [playback evidence](../../examples/physics-scene/evidence/fluid-871-playback-2026-10-09.md). This is an implementation speedup for the admitted 256-particle profile, not a higher particle-count or browser-wide performance promise.

The optional `@barocss/physics/cad-proxy` subpath admits one selected BaroCAD sourceVersion 0 native Surface from an exact source string. Its modules separate native admission, input validation, copied binding types and Viewer pose mapping. It depends on the public `@barocss/cad` compiler. `admitCadSurfaceProxy(source, request)` creates a qualified `part:<model>.<surface>` or `fixture:<model>.<surface>` Physics body from the original Surface control-net bounds in right-handed XYZ millimetres. A sphere encloses the control-net AABB; a box uses its axis-aligned half-spans plus a declared minimum half-extent. The result reports the original IDs, source revision, source center and a shape-loss label. Native rational Surface weights are positive under the CAD compiler profile, so the control net is a conservative envelope; this is not exact Surface collision. Dynamic bodies need explicit mass and may declare a starting offset. Body lengths convert by 0.001 to metres. `assertCadProxyCurrent` compares both the complete source string and caller revision. A change throws `STALE_SOURCE` until explicit re-admission. `cadProxyPose` checks that binding and maps an accepted Physics body pose back to Viewer millimetres, including rotation about the source center. The host owns world replacement and Viewer frame application. See [PHYS-10 #773](https://github.com/barocss/barocss/issues/773#issuecomment-6060408936) and the [native Viewer consumer](../../examples/physics-cad-scene/README.md).

The optional `@barocss/physics/replay` subpath saves an admitted scene and accepted fixed-step command log. `createPhysicsScene(world,{revision,sourceRevision})` copies and validates a version 1 scene; use `sourceRevision:null` for a scene without a CAD source. `createPhysicsReplaySession(scene)` owns a world with `step(commands?)`, `getState()`, `getScene()`, `saveSnapshot()` and `dispose()`. A saved version 1 snapshot includes that scene, one command frame per accepted step and the complete final state. `restorePhysicsReplaySession(snapshot,expectedScene)` checks exact scene/config and source revision identity, replays in a new world, and compares the final state within 1e-12 absolute/relative numeric tolerance. Changed revisions use `STALE_SNAPSHOT`; damaged or unsupported data uses `INVALID_SNAPSHOT`. Input and output are copied JSON-compatible data; object key insertion order does not change scene identity. The profile admits at most 512 recorded steps, 4096 total commands, a 128 Ki-code-unit scene and a 1 Mi-code-unit snapshot. It does not import arbitrary body state, migrate old versions or promise bitwise cross-platform results. See [PHYS-11 #774](https://github.com/barocss/barocss/issues/774#issuecomment-6060601264).

The host owns time and rendering. Physics uses metres, kilograms and seconds. Convert Viewer/CAD millimetres at the host boundary.

```ts
import { createPhysicsWorld } from '@barocss/physics';

const dt = 1 / 120;
const world = createPhysicsWorld({
  fixedStepSeconds: dt,
  gravityMps2: [0, -9.81, 0],
  bodies: [
    { id: 'part:ball', kind: 'dynamic', shape: { kind: 'sphere', radiusM: 0.15 },
      positionM: [0, 2, 0], velocityMps: [0, 0, 0], massKg: 1, restitution: 0.25 },
    { id: 'fixture:floor', kind: 'static', shape: { kind: 'box', halfExtentsM: [1, 0.2, 1] },
      positionM: [0, 0.2, 0], restitution: 0.25 },
  ],
});

const state = world.step(dt); // One caller-requested fixed step, no hidden clock.
console.log(state.bodies, state.contacts);
world.step(dt, [{ kind: 'force', bodyId: 'part:ball', forceN: [0, 2, 0] }]);
world.step(dt, [{ kind: 'impulse', bodyId: 'part:ball', impulseNs: [0, 0.5, 0] }]);
world.dispose();
```

`step(dt, commands)` accepts at most 64 dense, plain-object commands per step: `{kind:'force',bodyId,forceN}`, `{kind:'impulse',bodyId,impulseNs}`, `{kind:'torque',bodyId,torqueNm}`, `{kind:'angularImpulse',bodyId,angularImpulseNms}`, or `{kind:'kinematicTarget',bodyId,positionM}`. Each body may receive one command of each applicable kind per step. Force and torque act for one step; impulses change velocity once. A kinematic body has `kind:'kinematic'`, a sphere or box shape, position and restitution but no mass or input velocity. A target is an absolute metre position for this step; the reported velocity is target movement divided by `dt`. Without a new target it holds position and reports zero velocity. Only dynamic bodies receive force, impulse, torque or angular impulse. Kinematic bodies contact dynamic spheres but do not respond to impulses. Static/kinematic pairs are not reported.

Commands are validated before a candidate step. Dynamic integration applies impulse, then gravity and force, then position; collision resolution follows. Input order does not change the result. `getState()` and `step()` return copies. A failed step leaves the world at its last accepted state.

Dynamic bodies have an optional local-to-world `orientation: [x,y,z,w]` quaternion and `angularVelocityRadps: [x,y,z]`, both in the right-handed world frame. The defaults are identity and zero. Static/kinematic bodies can declare a fixed orientation but do not rotate during a step. The initial quaternion must have unit norm within 1e-6 and is normalized on admission. Sphere inertia is `2/5 × massKg × radiusM²`; an optional positive `inertiaKgM2` scalar overrides it for spheres only. A solid box uses local diagonal inertia `massKg/3 × [hy²+hz²,hx²+hz²,hx²+hy²]`. A capsule uses a labelled isotropic proxy inertia `2/5 × massKg × (radiusM+halfLengthM)²`. Every body state reports copied orientation and angular velocity; a dynamic body reports its scalar or diagonal inertia. World-frame torque and angular impulse use the orientation-transformed inverse inertia. The next angular velocity sets an axis-angle delta for this step. Left multiplication applies that delta in world coordinates, then the quaternion is normalized. Angular speed components are limited to ±1000 rad/s and angular displacement to 10 radians per step. See [PHYS-04 #767](https://github.com/barocss/barocss/issues/767#issuecomment-6058865060) and [PHYS-05 #768](https://github.com/barocss/barocss/issues/768#issuecomment-6058939158) for frozen fixtures and exclusions.

A capsule's segment lies on its local Y axis from `-halfLengthM` to `+halfLengthM`, with radius `radiusM` around it. All shape lengths are 0.0001–1000 m. The admitted pair families are sphere/sphere, sphere/oriented-box, sphere/capsule, oriented-box/oriented-box, capsule/oriented-box and capsule/capsule. Capsule/box finds the closest capsule-axis point to the oriented box; capsule/capsule finds closest points on their two axes. Coincident axes use a deterministic ID-based fallback normal. Box/box uses a deterministic 15-axis separating-axis check and one approximate support-midpoint contact point. Contact state reports a copied world-metre `pointM`. The solver uses velocity at that point, including `ω×r`, and applies equal/opposite linear and angular normal impulses. Position correction remains translational. This is a one-point manifold and does not establish stable capsule stacks or exact compound-capsule inertia. Sensors use the same admitted shape pairs without impulse. Sphere overlap and ray queries read oriented boxes and capsules as well. See [RIGID-00 #819](https://github.com/barocss/barocss/issues/819).

For the one-point box/box contact, a support axis perpendicular to the chosen normal uses the face centre on that axis. This removes the arbitrary far-corner torque in a symmetric box-on-floor fixture. It does not provide a multi-point manifold or guarantee stable off-centre stacks. See [RIGID-00a #848](https://github.com/barocss/barocss/issues/848).

Any body may declare optional `friction:{static,dynamic}` coefficients with `0 <= dynamic <= static <= 2`; both default to zero. A pair combines matching coefficients by geometric mean. After each normal impulse, the solver evaluates tangential velocity at the point, including angular velocity. It cancels slip when the required impulse fits within `μ_static × normalImpulse`; otherwise it applies at most `μ_dynamic × normalImpulse` opposite slip. Each physical contact reports a copied, accumulated world-vector `tangentImpulseNs`. There is no impulse cache, warm start or persistent static constraint. The fixed sphere stack probe establishes only its recorded 240-step drift/penetration bounds. See [PHYS-06 #769](https://github.com/barocss/barocss/issues/769#issuecomment-6059055828) for the frozen fixture and limits.

The optional world setting `contactMode:"persistent-box-v1"` admits at most four bodies. For a box/box contact with a face normal, it clips the incident face to the reference face, keeps up to four deterministic contact points, and reuses their bounded accumulated normal and friction impulses on the next accepted fixed step. It reports one copied contact summary per body pair. Edge/edge and non-box contacts keep the one-point path. The default world path retains the earlier one-point behavior. This mode establishes the recorded centred and 0.05 m offset stack fixtures only; it does not guarantee arbitrary tilted stacks, high-speed impacts or engineering loads. See [RIGID-01 #820](https://github.com/barocss/barocss/issues/820).

The opt-in `sceneMode:'large-v1'` admits 1–64 bodies with `broadPhase:'aabb'`; it excludes joints, CCD and `persistent-box-v1`. Each body can declare `collisionFilter:{categoryBits,maskBits}` with integer 16-bit values (category 1–65535, mask 0–65535). The default is category 1 and mask 65535. Both bodies must admit each other's category for a contact or sensor event. Filters are fixed at world creation. Dynamic states expose copied `sleeping` booleans. A supported dynamic contact island sleeps after 60 consecutive steps with all linear and angular speeds at most 0.02 in SI units. Static and kinematic fixtures support islands but do not join separate dynamic groups. Nonzero force/impulse/torque, contact with an awake dynamic body and moving kinematic support wake affected bodies. Sleeping contacts still report events. The 63-sphere floor fixture proves this bounded profile; it does not establish arbitrary 64-body stack stability, a broad collision matrix at this scale or a general speedup. See [RIGID-02 #821](https://github.com/barocss/barocss/issues/821) and `examples/physics-scene/large-scene-probe.mjs`.

Optional `joints` connect one static/kinematic A body to one uniquely jointed dynamic B body. At most eight dense fixed/hinge records use qualified IDs and body-local `anchorALocalM`/`anchorBLocalM` in metres; the initial world anchors must coincide within 1e-6 m. A fixed joint preserves the initial relative orientation and common anchor. A hinge declares a unit `axisWorld` and a `limitRad:[min,max]` within ±π/2 including zero. It allows only signed twist about that axis from B's initial orientation and clamps at the limits. Joint projection runs after each contact pass; a connected A/B collision pair is disabled. State reports copied per-step `joints` with linear and angular reaction impulses, plus hinge angle. Reactions are the dynamic B velocity corrections caused by this bounded projection solver. They are not certified mechanical loads. See [PHYS-07 #770](https://github.com/barocss/barocss/issues/770#issuecomment-6059121440) for the first anchored profile.

One `fixed` joint may instead connect exactly two dynamic spheres and no other bodies or joints. The solver distributes anchor and orientation corrections by inverse mass/inertia and disables contact between the connected bodies. The first measured fixture is two 1 kg spheres separated by 0.2 m under one 0.2 N·s impulse; its native and Viewer checks are in `examples/physics-scene/dynamic-fixed-pair-probe.mjs` and `examples/physics-viewer-scene/joint-demo.html`. Joint state reports the impulse on B; the equal/opposite A correction is checked in the fixture. Other mass ratios, large rotations and complex contact networks are not accepted performance or accuracy profiles. This dynamic pair has no motor, break force, cycle or CAD-authored assembly constraint. See [RIGID-04 #823](https://github.com/barocss/barocss/issues/823#issuecomment-6072507713).

An anchored `hinge` may declare `motor:{targetSpeedRadps,maxImpulseNms,maxReactionNms}`. The target speed is within ±2 rad/s; the per-step motor impulse cap is positive and at most 0.05 N·m·s; the per-step constraint reaction cap is positive and at most 1 N·m·s. The motor impulse is reported separately as `motorImpulseNms`. The motor stops pushing outward at a hinge limit. A constraint reaction above the configured cap fails the step with `NUMERIC_LIMIT` and keeps the last accepted state. This is a refusal bound, not a break-force model. The first fixture uses one static anchor, one 1 kg sphere, zero gravity, 1/120 s steps and a +Z hinge; see `examples/physics-scene/hinge-motor-probe.mjs` and `examples/physics-viewer-scene/motor-demo.html`.

One `hinge` may instead connect exactly two dynamic spheres at the same centre. This planar profile requires zero gravity, zero initial motion, identity initial orientations and zero local anchors. Only angular commands along the hinge axis are admitted. Its optional motor drives the relative speed of B against A with equal and opposite impulses; the reaction cap retains the last accepted state on overload. A measured pair of 1 kg, 0.1 m spheres reaches opposite ±0.25 rad/s at step 10 and 0.48125 rad relative angle at step 120. See `examples/physics-scene/dynamic-hinge-motor-probe.mjs` and `examples/physics-viewer-scene/dynamic-hinge-demo.html`. Offset anchors, gravity, linear commands, off-axis motion, multi-joint assemblies and calibrated break laws are outside this profile.

One separate offset-hinge profile connects exactly two 1 kg dynamic spheres with 0.1 m radius. Their initial centres are `[-0.1,0,0]` and `[0.1,0,0]` m; local anchors `[0.1,0,0]` and `[-0.1,0,0]` m meet at one pivot. It admits one planar +Z hinge with `limitRad:[-0.8,0.8]`, a motor targeting 0.5 rad/s relative speed with 0.0001 N·m·s motor impulse and 0.01 N·m·s reaction caps, zero gravity and no linear or off-axis commands. The caller steps at 1/120 s. Joint state copies the reaction on B; a reaction above `maxReactionNms` refuses the candidate and retains the accepted world and Viewer frame. That cap is a numeric limit, not a material break strength. At step 120 the measured relative angle is 0.4809513021838483 rad. The [numeric probe](../../examples/physics-scene/offset-hinge-probe.mjs), [Viewer demo](../../examples/physics-viewer-scene/offset-hinge-demo.html?step=120) and [#939 merged receipt](https://github.com/barocss/barocss/issues/939#issuecomment-6077079018) cover this one fixture. Other mass ratios, nonzero gravity, arbitrary offset axes, multiple joints, exact CAD collision and calibrated loads remain outside it.

Set `ccd:true` on a dynamic sphere to prevent it from crossing a thin static box in one step. The first opt-in profile admits exactly one dynamic sphere, 1–8 static nonsensor oriented boxes, and no joints or other bodies. The sphere center sweeps through each box-local axis-aligned bound expanded by its radius. The earliest entry fraction wins, with fixture ID breaking equal-fraction ties. The candidate stops at the entry point with a 1e-9 m inward offset so the discrete contact solver can respond. An initial center inside an expanded box uses the discrete solver. Expanded-box corners can conservatively report a hit before exact sphere/box contact. See [PHYS-08 #771](https://github.com/barocss/barocss/issues/771#issuecomment-6059234992) for that profile.

A second opt-in CCD profile admits exactly two nonsensor dynamic spheres, exactly one marked `ccd:true`, zero gravity and no joints. It sweeps their relative centres and stops both at the first entry, with a total inward offset of 1e-9 m so the discrete contact solver can respond. The reported `fixtureId` names the **other dynamic sphere**, and `normalFixtureToBody` points from it to the marked sphere. Initial overlap/touch and a missing entry use the discrete solver. See [RIGID-05 #824](https://github.com/barocss/barocss/issues/824) and `examples/physics-scene/ccd-pair-probe.mjs`.

A third opt-in CCD profile admits exactly one dynamic axis-aligned box marked `ccd:true` and one static nonsensor axis-aligned box, with no joints or `persistent-box-v1`. It sweeps the dynamic centre against the static bounds expanded by both half-extents, then stops at first entry with a 1e-9 m inward offset. Initial overlap and no-entry motion use the discrete solver. A nonzero angular command fails before stepping; if contact creates rotation, that candidate fails and the last accepted state remains. This profile fixes the named 0.002 m-thick CAD Surface proxy fixture, not arbitrary tilted or moving boxes. All CCD profiles report copied `{bodyId,fixtureId,toiFraction,normalFixtureToBody}` records and stop without integrating the remaining fraction of the step. Other CCD configurations refuse creation; omitted `ccd` retains the discrete solver. Capsule sweeps, general oriented-box CCD and more than two dynamic CCD bodies are unsupported. See [RIGID-05a #864](https://github.com/barocss/barocss/issues/864) and `examples/physics-scene/thin-box-ccd-probe.mjs`.

Optional `broadPhase:'aabb'` filters the existing eligible pair list before narrow-phase detection. Omit it for the original direct pair path. Bounds enclose spheres by radius, oriented boxes by projected half-extents, and oriented capsules by radius plus projected local-Y half-segment. They are updated from each moving body at the start of every solver pass and immediately after its contact correction; static bounds are reused during that step. Intervals overlap inclusively with 1e-9 m slack. `state.pairStats` is a copied per-step `{eligiblePairs,candidatePairs,aabbTests}` count across eight passes. Direct mode has candidatePairs equal to eligiblePairs and zero AABB tests. AABB mode reports one test for each eligible pair; candidatePairs counts narrow-phase calls. The initial state has zeros, and failed steps retain the prior counts. The fixed 32-body/120-step compiled fixture reduced candidate calls from 29,760 to 960 with matching recorded contacts and poses. Its one-machine wall time and heap-use change are observations, not general performance or allocation guarantees. The direct option remains available for contact cascades outside that fixture. In `large-v1`, layer filtering removes pairs before these counts, and sleeping pairs are checked on the first pass but can skip later passes; `aabbTests` can therefore be lower than `eligiblePairs`. See [PHYS-09 #772](https://github.com/barocss/barocss/issues/772#issuecomment-6060293632) for the frozen contract.

`state.events` reports `begin`, `stay` and `end` for the last accepted step. Events carry sorted body IDs and `kind:'contact'|'sensor'`. A static or kinematic collider can use `sensor:true`: it reports overlap events with a dynamic sphere but produces no physical contact, impulse or position correction. Initial overlap begins on the first step. The array is copied with state and is retained after a failed step.

`world.overlapSphere({centerM,radiusM,includeSensors?})` returns lexically sorted body IDs. `world.raycast({originM,direction,maxDistanceM,includeSensors?})` returns the nearest `{bodyId,distanceM}` or `null`; direction must be unit length within 1e-9. A ray starting inside a shape reports distance zero. Both queries read the last accepted state; they do not advance the world. Sensor inclusion defaults to true. Query positions are within ±10000 m, radius is 0.0001–1000 m, and ray distance is 0.0001–10000 m. Spheres, oriented boxes and capsules are admitted. Invalid queries use `INVALID_QUERY` and keep accepted state. See [PHYS-03 #766](https://github.com/barocss/barocss/issues/766#issuecomment-6058738723) for the original event and query rules.

`PhysicsError.code` identifies `INVALID_CONFIG`, `INVALID_STEP`, `INVALID_COMMAND`, `INVALID_QUERY`, `INVALID_SNAPSHOT`, `STALE_SOURCE`, `STALE_SNAPSHOT`, `WORLD_LIMIT`, `NUMERIC_LIMIT` or `DISPOSED`.

Limits: 1–32 bodies by default or 1–64 in `large-v1`, at least one dynamic body, 3600 steps, fixed step 1/240–1/30 s. Each position component is within ±10000 m, velocity and gravity components within ±1000 m/s, mass 0.000001–1000000 kg, sphere radius and box half extents 0.0001–1000 m, restitution 0–1. Force and torque components are within ±1000000 N or N·m; linear and angular impulse components are within ±100000 N·s or N·m·s. One step refuses movement or measured penetration above 10 m. Body IDs are unique ASCII identifiers, up to 64 characters, starting with a letter. Contact pairs have ascending IDs; `normalAtoB` points from A to B. See [Issue #751](https://github.com/barocss/barocss/issues/751) for v0 and [PHYS-02 #765](https://github.com/barocss/barocss/issues/765#issuecomment-6058662978) for linear control.
