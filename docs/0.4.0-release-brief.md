## 현재 절차의 위험

초기 `release.yml`은 수동 `workflow_dispatch`에서 Changesets publish를 허용했다. #73은 `develop`의 이 파일을 버전 PR 전용으로 바꿨다. #87은 `main`의 옛 토큰 게시 경로를 제거했고, #88은 이를 `develop`에 동기화했다. #81은 `main` PR/push에서 검사만 하고, `easylogic`의 `publish=true` 수동 실행에서만 OIDC 게시를 허용한다. #71은 당시 버전을 0.0.4로 올렸고, #90은 목표 0.4.0으로 갱신했다.

`develop` 보호 설정은 PR과 최신 `Test and Build` 검사를 요구한다. 승인 리뷰와 Pages 배포는 필수가 아니다. 저장소 Actions 기본 토큰 권한은 read이며, 기존 `release.yml`의 job 권한에는 `pull-requests: write`가 없다. 이 상태에서 Changesets가 버전 PR을 만들 수 있다고 가정하지 않는다.

공개 browser 0.0.3은 CommonJS `require` 경로를 표시하지만, 별도 Node 22 소비자에 설치해 `require('@barocss/browser')`를 실행하면 kit의 `ERR_PACKAGE_PATH_NOT_EXPORTED`로 실패한다. 0.4.0 후보는 이 경로를 제거하고 ESM import를 지원 경로로 명시한다. 기존 사용자가 CJS 경로를 기대했다면 변경을 알려야 한다.

PM이 정확한 `develop` SHA와 버전, Guard·Ship 근거를 확인한다. `main`이 후보의 조상이고 PR head가 현재 `develop` SHA인지 병합 직전에 다시 확인한다. 그 후보를 보통 PR로 `main`에 올리고, 필수 `build`·`test`와 대화 해결 뒤 `easylogic`이 직접 merge한다. `main` push에서는 npm 게시가 실행되지 않는다. `easylogic`이 `main`의 정확한 SHA와 버전, PM 기록을 넣고 **Npm release**를 수동 실행할 때 `publish=true`로 명시해야 게시가 시작된다. 기본값 `false`는 검사만 한다. `npm` 환경은 `main` 전용으로 확인됐다. 자세한 조건은 [수동 릴리스 설계](automatic-release.md)에 있다.

## 버전 규칙과 릴리스 순서

세 패키지는 `.changeset/config.json`의 `linked` 그룹이다. `baseBranch`는 `develop`, 내부 의존성 갱신 방식은 `patch`, 공개 범위는 `public`이다. 이 그룹에서는 변경을 기록한 패키지와 의존 패키지가 같은 목표 버전을 갖는지 최종 결과로 확인한다. Changesets의 linked 설정만으로 모든 패키지가 항상 자동으로 올라간다고 가정하지 않는다.

**0.4.0 버전:** PR #71은 당시 버전과 lockfile을 0.0.4로 올렸다. [PR #90](https://github.com/barocss/barocss/pull/90)은 세 패키지의 매니페스트를 0.4.0으로 맞췄다. [병합 커밋 CI](https://github.com/barocss/barocss/actions/runs/35846116062)는 통과했다. 최종 후보 SHA에서 packed 내부 의존성, npm 버전 충돌, 사이트 빌드를 다시 확인한다. PR #71의 변경 내역과 Guard 보고서는 release notes의 근거로 쓴다.

**다음 릴리스부터:** 변경 PR마다 영향 패키지와 `patch`/`minor`/`major`를 명시한 changeset을 추가한다. `develop` 병합 뒤 **Npm version PR**을 수동 실행한다. 생성된 `changeset-release/develop` PR의 버전, 세 `CHANGELOG.md`, 내부 의존성, lockfile을 검토하고 CI 통과 후 병합한다. Guard·Ship 근거와 설정 검증이 끝나면 PM은 정확한 `develop` SHA와 버전으로 준비 기록을 남긴다. 후보의 현재 SHA와 `main` 조상을 확인하고 보통 `main` PR을 거친 뒤 `easylogic`이 직접 merge한다. npm 게이트는 [수동 절차](automatic-release.md)를 따른다. 버전 정책을 바꿀 때는 PM이 세 패키지의 공개 API 영향과 0.x 변경 의미를 문서로 결정한다.

## 게시 전 Go / No-go 기준

0.4.0 Go에는 정확한 `develop` SHA의 CI·사이트 빌드·pack·npm 충돌 검사, Guard·Ship 근거, Docs 실사이트 검사, PM의 SHA·버전 준비 기록이 모두 필요했다. 보호된 `main` PR의 `build`·`test`와 대화 해결도 필수였다. 마지막 npm 게이트는 `easylogic`의 `publish=true` 수동 실행이었다. 이 조건을 거쳐 OIDC 게시가 완료됐다.

## 실패와 사후 확인

- **게시 전 실패:** 워크플로를 멈춘다. 코드와 버전을 고친 새 PR을 만들고 CI·dry-run을 다시 실행한다.
- **일부 패키지만 게시:** 세 npm 버전을 먼저 조회하고 결과를 기록한다. 이미 게시한 버전은 재게시하지 않는다. 실패 원인을 고친 뒤 같은 버전의 남은 패키지만 게시할 수 있는지 검토한다. 자동 재실행은 하지 않는다.
- **태그 또는 Release만 누락:** npm 게시 결과와 실제 커밋을 확인한 뒤 누락 기록을 복구한다. 게시 실패를 GitHub Release 성공으로 보고하지 않는다.
- **0.4.0 결함:** 영향을 받은 0.4.0에 npm deprecate 안내를 붙이고 수정한 patch 버전을 새로 낸다. 이미 배포된 0.4.0을 되돌리거나 같은 번호로 덮어쓰는 절차를 계획하지 않는다.
- **게시 후 24시간:** npm 설치, 패키지별 import/require/타입, browser CDN 경로, 세 Releases·태그, 관련 Issue와 오류 보고를 확인한다. PM이 고객 안내 필요 여부를 정한다.

## Release notes 초안

**BaroCSS 0.4.0**은 kit의 Context 상태 격리, 클래스별 `!important` 처리, 중복되거나 중첩된 `@property` 출력 수정, browser의 DOM 변경·설정 갱신·종료 처리, server의 빈 입력 처리를 개선한다. 세 패키지의 배포 export·타입·라이선스 파일을 점검했고, browser와 server 테스트를 루트 검사에 포함했다. browser는 ESM import를 사용한다. 0.0.3에 표시됐지만 동작하지 않던 CommonJS `require` 경로는 제거했다. 선택한 Tailwind CSS 4.1.13 입력은 고정 fixture와 Chromium 렌더링으로 비교했다. 이 검사는 Tailwind 전체 호환성 보증이 아니다. API 또는 설치 방식에 영향을 주는 변경은 PR #71의 최종 diff와 패키지 README를 기준으로 게시 직전에 다시 확인한다.

## barocss-editor와의 차이 및 준비 작업

[barocss-editor의 버전 PR](https://github.com/barocss/barocss-editor/blob/main/.github/workflows/npm-version.yml)은 `main`에서 Changesets version PR을 만든다. [npm 릴리스](https://github.com/barocss/barocss-editor/blob/main/.github/workflows/npm-release.yml)는 `main`의 수동 실행, 기본 `publish=false` 검사, 명시적 `publish=true` 게시를 쓴다. BaroCSS도 이 게시 승인 모델을 따른다. 단, 0.4.0의 버전 PR은 현재 개발 브랜치인 `develop`에 유지한다.

BaroCSS는 세 패키지의 검사된 tarball을 그대로 npm OIDC Trusted Publishing으로 게시하도록 PR #81에서 준비했다. Mento의 npm UI 확인에서 세 패키지의 GitHub 조직 `barocss`, 저장소 `barocss`, 파일 `npm-release.yml`, 직접 `npm publish` 설정이 일치했다. npm 사이트의 환경 이름은 비어 있으며 선택 항목이다. GitHub Actions의 `npm` 환경은 별도로 `main`만 허용한다. 실제 OIDC 교환은 승인된 게시에서만 검증된다.

설정 순서는 다음과 같다.

1. #87에서 `main`의 옛 토큰 게시 워크플로를 제거하고 `build`·`test`를 준비했다. `main`의 필수 승인 수는 0이고 필수 검사·대화 해결·관리자 보호는 유지한다. #88로 `develop`에 동기화했다. GitHub App은 사용하지 않는다.
2. GitHub의 `npm` 환경은 `main`만 허용하도록 이미 확인됐다. 최종 PM GO 뒤 `easylogic`이 수동으로 `publish=true`를 입력한다. npm 토큰을 추가하지 않는다. 저장소 Actions secret-name 목록은 비어 있다.
3. `develop`은 PR과 최신 `Test and Build`를 유지한다. PM의 정확한 후보 SHA와 `main` 조상을 병합 직전에 확인하고, 보통 `main` PR을 통해 승격한다. `main` push는 npm 게시 없이 검사만 한다.
4. `easylogic`은 `main`의 정확한 SHA·세 패키지 버전·PM 준비 기록을 넣고 수동 `publish=true`를 실행한다. 기본 `publish=false`는 검사만 한다. [npm 공식 문서](https://docs.npmjs.com/trusted-publishers/)에 따라 Node 22.22.0과 npm CLI 11.5.1로 OIDC 게시를 한다. `npm whoami`는 OIDC 검증에 쓰지 않는다.
