# #446 decision report — offline phase

**Decision status: blocked, not a product recommendation.** The current evidence cannot determine whether BaroCSS adds measurable value to repeatedly edited json-render UI. The smallest justified next step is an isolated, pinned install of the official json-render React renderer and an offline browser replay of this frozen contract. No BaroCSS UI layer, adapter or package API change is supported by this phase.

## What this phase established

- [`contract.mjs`](contract.mjs) freezes settings, dashboard and kiosk semantics; four stages per scenario; three catalog styling arms plus a matched build-only control; and the interaction order. The build control's class inventory is fixed at the initial stage. The contract hash is `3b62dbe15a670e7ae1708af113cdda5770fb9198f85d8ebef96e63469020523f`.
- [`offline-preflight.json`](offline-preflight.json) contains 48 explicit cells. All are `blocked:official-renderer-unavailable` with null measurements. This worktree has no installed `@json-render/core`, `@json-render/react`, React, React DOM or Playwright. The local manifests identify `@barocss/browser` and `@barocss/kit` 0.11.1 and Tailwind CSS 4.3.3; these are package metadata, not proof that those dependencies were executed here.
- [`../json-render-376/NOTES.md`](../json-render-376/NOTES.md) and [`../json-render-376/result.json`](../json-render-376/result.json) preserve one-shot prior outputs. They suggest that a catalog admitting `className` can reach high one-shot visual fidelity, while class-token policy remains a BaroCSS concern. They do not measure edited state, focus, actions or unstyled frames, and they cannot establish a multi-turn success rate.
- The [current json-render React guide](https://github.com/vercel-labs/json-render/blob/c2600d73908ed505e6d726f5b6f969ba8f597ce7/skills/react/SKILL.md) places component/prop permission in the catalog and input binding/action behavior in the renderer/provider. The [A2UI v1.0 protocol](https://github.com/a2ui-project/a2ui/blob/ec12ba915ab21725929430bd14bcef04e5ee7f12/specification/v1_0/docs/a2ui_protocol.md) permits custom catalogs; #376's v0.9 basic-catalog styling gap is not a whole-protocol limit. The [AG-UI client guide](https://github.com/ag-ui-protocol/ag-ui/blob/b8ebd02c84a3a2757990da47aebf7c55b708b1ef/docs/quickstart/clients.mdx) describes event transport rather than a required CSS runtime.

## Unmeasured outcomes and attribution

No scenario has a rendered screenshot, computed-style comparison, input/focus/action result, frame count or host-style delta from this phase. No cell is a pass. The absence of an official renderer prevents attribution of any hypothetical failure to catalog expressibility, React state handling, CSS generation, or BaroCSS. The prior one-shot study used worker-authored references, heuristic visual checks and one output per cell; prompt wording, catalog choice and reference tuning are alternative explanations for its scores.

Once dependencies are available, the runner must first verify schema/DOM/state. A missing component or changed user value/focus before an action is a renderer/state failure. If DOM and state are correct but computed style or stylesheet insertion is wrong, the failure is styling. A click-induced blur is expected browser behavior, so focus is recorded before the action click. Both failures together, missing timing evidence, or a blocked dependency are mixed/unknown. An unstyled-frame claim requires frame-by-frame evidence, not only a final screenshot. Host impact requires before/after computed style of an unchanged host sentinel.

## Preregistered follow-up, still unapproved

Install pinned official json-render core/React and their React peer dependencies in an isolated research directory, plus a pinned Playwright core and browser executable. Record exact package versions, resolved tarball integrity, browser version, OS, Node version, BaroCSS commit and theme CSS hash. No other renderer is an acceptable substitute. Independent Review must reproduce representative cells and inspect any failure attribution.

### Step 2: live-model reliability study, after a separate owner cost/safety approval

Freeze the three scenario briefs, catalog prompts, theme, edit instructions, JSON spec schema, examples, fixture hash above, random seeds (0–4), model IDs and generation settings before calling a model. Use 5 independent sessions per scenario × 3 styling arms × 2 tiers = **90 sessions**. Each session has initial generation plus three edits, for **360 responses**. Use the same user-input state at each edit; do not give the model hidden outcomes from another arm. Pair arms by scenario, seed and model tier. The build-only control replays the utility arm's exact outputs with its initial-stage class inventory, so it adds no model calls.

Candidate tiers for cost planning are Claude Haiku 4.5 and Sonnet 5. These are provisional model IDs, not authorization or an assumption about CLI billing. Set an operational cap of 3,000 billed input tokens and 1,000 billed output tokens per response; abort a session that cannot fit without truncating required context. At 180 responses per tier, the cap is 540,000 input and 180,000 output tokens per tier. Using the [Haiku 4.5 list price](https://www.anthropic.com/claude/haiku) of $1/$5 per million input/output and [Sonnet 5 list price](https://www.anthropic.com/news/claude-sonnet-5) of $2/$10, the estimated maximum base token charge is **$1.44 + $2.88 = $4.32**. A 20% planning margin is $5.19, rounded to **$5.20**. Prices were checked on 2026-09-27; confirm the actual provider, model IDs, billing route, rates and any cache/tool/tax charges immediately before a paid run. Do not infer that a subscription CLI session follows API list prices.

Record per response: raw output, prompt/response tokens, wall-clock latency, parse/schema/render failures, missing nodes, state/value/focus/action preservation, styling/host/frame outcomes and estimated billed cost. Report per-arm denominators, failures by cause, median and 95th-percentile latency, median token use, and paired per-scenario outcomes with uncertainty. Five repeats per cell are exploratory; do not claim statistical superiority from this sample. The live run remains blocked until the owner approves its provider, cost ceiling and safety boundary. No paid calls were made in this phase.

## Verification and next decision

The exact offline commands are in the #446 Issue body. Node.js 22.22.0 passes the contract tests; regenerating the preflight leaves no diff. The current conclusion is **insufficient evidence**. Planner should decide whether an isolated official dependency install is in scope for the next phase. After a genuine deterministic replay, Review should decide whether any remaining gap is a CSS runtime/style-contract issue or already handled by catalog/renderer/host responsibilities. Only then should Planner choose among an example, adapter, style contract, UI layer or no addition.
